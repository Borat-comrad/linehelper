## 6. Конфликты источников и версий

### 6.1. Фактические конфликты

Прямого фактического конфликта по девяти сценариям не найдено:

- legacy PDF описывает секции и руководителей верхнего уровня;
- structured source добавляет текущие typed записи сотрудников, подразделений и contact routes;
- процедурные инструкции описывают workflow;
- эти данные в проверенных местах дополняют друг друга, а не противоречат.

T06 иллюстрирует не конфликт, а разные роли:

### 6.3. Политика authority

Явной матрицы приоритетов в runtime нет.

Поиск `source_version`, `authority`, `knowledge_domain`, status/active по коду показал:

- `source_version` используется parser/indexer и `doctor` для отчётности;
- `knowledge_domain` помогает распознать structured organization chunks;
- retrieval/rerank не сравнивает версии источников;
- нет поля или функции `authority_level`;
- procedural-vs-org и operational-vs-semantic не разрешаются общей политикой.

В `answer_generator.py:957-1004` structured chunks получают фиксированный metadata boost, но это не source authority: дата, версия, active/inactive сущности и вид вопроса не сравниваются.

Ожидаемая политика должна быть явной:

- процедура процесса → процедурный документ;
- ответственный/сотрудник → актуальный active structured organization record;
- текущий статус/цена/остаток → операционная система;
- legacy PDF → fallback или исторический контекст, если structured record отсутствует;
- при конфликте → показать конфликт и применённое правило версии.

Сейчас такой политики нет — это архитектурный риск, даже хотя в девяти сценариях прямой конфликт не доказан.

## 9. Фундаментальные причины

### F1. Нет conversation-aware разрешения follow-up

Наблюдение: T01b обрабатывается как новый запрос.  
Сценарии: T01; разговорные короткие follow-up из test pack.  
Механизм: UI хранит сообщения только для отображения → `answer(question)` получает одну строку → analyzer/retrieval не знают исходного намерения.  
Системность: любой ответ «да», «нет», «коммерческое предложение», «в этот отдел», фамилия или уточнение параметра теряет исходный вопрос.

### F2. Intent validation использует лексический приоритет вместо семантической декомпозиции

Наблюдение: «Кто отвечает за отгрузку?» становится операционным запросом 1С.  
Сценарии: T03, T06; класс 2 «Кто отвечает за отгрузку?»; класс 5 «Кто выпускает заказ клиенту?».  
Механизм: `_is_one_c_operational_lookup_question` срабатывает по словам `заказ`, `склад`, `отгрузка` раньше `_is_roles_responsibility_question`; тип факта «responsibility» игнорируется. Equipment intent одновременно объявлен строго source-dependent, хотя валидатор удаляет preferred sources.

### F3. Clarification не ограничен доказанной неоднозначностью и intent

Наблюдение: полностью ясный T09 уходит в уточнение; в одном replay fallback выдаёт КП/ЦКП, в других — лишний вопрос о типе документа.  
Сценарии: T09. Шесть контрольных вопросов без КП не показали массового переноса KP intent, то есть prompt contamination или state leakage не подтверждены.  
Механизм: любой план `needs_clarification + answer_type=clarification` принимается; если текста вопроса нет, `_query_plan_clarification` всегда возвращает `CLARIFY_KP_MESSAGE`, не проверяя `intent` и наличие `КП`.

### F4. Retrieval и context selection не компонуют дополняющие доказательства

Наблюдение: T02 теряет три из четырёх соседних правил; T08 не связывает policy с organization records; T07 заполняет context нерелевантными routes.  
Сценарии: T02, T07, T08; классы 2 и 4.  
Механизм:

- retrieval limit 5 на query;
- dedupe сохраняет единственный экземпляр chunk, не гарантируя лучший score среди всех запросов;
- max context 3;
- глобальный relative cutoff 0.65;
- score применяется как универсальная мера полноты;
- context builder не умеет потребовать «все sibling rules» или «procedure + responsible».

### F5. Модель ответственности недостаточно типизирована

Наблюдение: система путает ответственного исполнителя, руководителя подразделения, контакт маршрута, кадровика, ЭДО и оформителя документов.  
Сценарии: T04, T06, T07, T08; класс 2, класс 3.  
Механизм: `responsibility_route` покрывает 22 крупных направления, но не содержит внутренних документов, рабочих мест, оборудования и большинства процедур. Procedure chunks не имеют отношений к organization entities. Существующие record keys не используются relation-aware resolver’ом.

### F6. Evidence/partial-answer policy слишком грубая

Наблюдение: для одних intents пустой preferred context даёт гарантированный отказ; для любого другого известного intent любой непустой chunk автоматически достаточен.  
Сценарии: T03, T05, T07, T08.  
Механизм: `has_sufficient_context` возвращает `True` для любого `intent != unknown`; отсутствует проверка требуемого типа факта и покрытия частей вопроса. Генератор не обязан сообщить доступную часть и точную границу отсутствующих данных.

### F7. Нет исполнимой политики authority/version и единой metadata taxonomy

Наблюдение: structured source имеет версию, legacy/procedure chunks — нет; chunk 29 с полноценной процедурой имеет общий `doc_type=reference`.  
Сценарии: T03 и все organization/procedure комбинации; потенциально T06–T08.  
Механизм: версии показываются в `doctor`, но не участвуют в retrieval/rerank/conflict resolution. Нет authority matrix, active-version selection и проверяемого приоритета procedure/org/operational.

## 10. Концепция системных исправлений

### F1 → Conversation-aware query resolution

- Наблюдаемое поведение: короткий follow-up теряет исходный intent.
- Подтверждение: T01; код UI.
- Концепт: перед analyzer передавать ограниченную структурированную history; строить `resolved_question`, сохраняя исходный predicate и заменяя только неоднозначный slot.
- Слой: conversation state, Query Analyzer, retrieval.
- Риски: неправильное наследование устаревшего контекста; утечка предыдущей темы в новый вопрос.
- Регрессии: явный follow-up; смена темы; «это другое»; два последовательных уточнения; fresh session.
- Приоритет: P0.

### F2 → Intent decomposition и type-first operational boundary

- Наблюдаемое поведение: слово «отгрузка» побеждает конструкцию «кто отвечает».
- Концепт: сначала определить требуемый тип факта (`responsible_person`, `procedure`, `current_status`, `price`, `availability`), затем предмет. Операционный boundary применять только к status/value lookup, а не ко всем упоминаниям операционной сущности.
- Слой: Query Analyzer validation, intent schema.
- Риски: role-вопросы могут ошибочно открыть semantic ответ там, где спрашивается фактический статус.
- Регрессии: пары «кто отвечает за заказ?» / «какой статус заказа?», «кто ведёт склад?» / «что осталось на складе?».
- Приоритет: P0.

### F3 → Intent-scoped clarification with proof

- Наблюдаемое поведение: ясный вопрос уточняется; generic fallback подставляет KP.
- Концепт: clarification допустим только с `ambiguity_span`, `candidate_meanings` и непустым intent-specific question. KP/CKP разрешать только при фактическом regex-match сокращения. Невалидный clarification plan отклонять в safe fallback к retrieval, а не к KP.
- Слой: Query Analyzer validation, ambiguity detection.
- Риски: слишком строгая проверка может заставить отвечать на реально двусмысленный вопрос.
- Регрессии: вопросы с/без КП; ясные распоряжения; неизвестное сокращение; короткие местоимения без history.
- Приоритет: P0.

### F4 → Coverage-aware multi-stage retrieval и context composition

- Наблюдаемое поведение: соседние правила и organization evidence отбрасываются.
- Концепт: intent-specific retrieval stages; sibling expansion по `logical_unit_title`/source; diversity slots; best-score dedupe; relation join; context coverage по требуемым subfacts, а не один глобальный ratio.
- Слой: retrieval, merge, rerank, context builder.
- Риски: рост prompt и latency; добавление слабых chunks.
- Регрессии: четыре правила одного документа; procedure + responsible; role + contact; конфликтующие versions.
- Приоритет: P0.

### F5 → Typed responsibility resolver

- Наблюдаемое поведение: руководитель, исполнитель, адресат и оператор смешиваются.
- Концепт: универсальный resolver с типами отношений `owns_function`, `primary_contact`, `heads_unit`, `executes_step`, `receives_document`, `fallback_contact`; query entity → function/process → relation → role → active employee/contact/source/version.
- Слой: entity resolver, knowledge model, retrieval.
- Риски: неверная типизация существующих свободных текстов; необходимость ручной валидации ключевых routes.
- Регрессии: внутренний/кадровый/ЭДО; доставка/отгрузочные документы; рабочие места/IT/промышленное оборудование.
- Приоритет: P1.

### F6 → Confidence-aware partial answers

- Наблюдаемое поведение: либо полный отказ, либо автоматический pass любого известного intent.
- Концепт: evidence schema по subclaims; ответ обязан перечислить подтверждённые части, явно назвать отсутствующую часть и уточнять только slot, без которого нельзя продолжить. Запрещать советы о людях/отделах без source.
- Слой: evidence gate, answer planner, prompt.
- Риски: чрезмерно длинные ответы; ложное чувство полноты.
- Регрессии: procedure без адресата; роль только для части составного вопроса; operational status + static policy.
- Приоритет: P0.

### F7 → Source authority matrix и metadata contract

- Наблюдаемое поведение: version есть не у всех; doc type процедуры может быть `reference`.
- Концепт: нормализовать `knowledge_domain`, `doc_type`, `source_version`, `valid_from/to`, `authority_level`, `active`; задать матрицу по типу факта; диагностировать неизвестную/неупорядочиваемую версию.
- Слой: ingestion metadata, retrieval/rerank, conflict resolver.
- Риски: ошибочный приоритет приведёт к систематически неверным именам; миграция metadata.
- Регрессии: structured vs legacy; procedure vs org; active/inactive employee; semantic vs operational.
- Приоритет: P1.

## 13. Риски

1. Исправление ranking без изменения intent precedence не поможет T06: правильные chunks уже найдены, но отбрасываются политикой.
2. Простое увеличение context limit может добавить ещё больше нерелевантных routes и не гарантирует полноту T02.
3. Словарь с фамилиями или отдельными вопросами быстро устареет и замаскирует отсутствие typed relations.
4. Автоматический приоритет structured source опасен, пока `2025-12-17` не сопоставлен с PDF `2026-03-03` как бизнес-версия.
5. History может загрязнять новую тему; нужен явный detector продолжения.
6. Live Ollama analyzer недетерминирован даже при temperature 0: T09 менял clarification между повторами. Regression pack должен проверять invariants и повторяемость.
7. Контактные данные являются изменяемыми фактами; должны иметь active/version lifecycle.
8. T05 нельзя превращать в строгий golden test без исходного пользовательского вопроса.
